# 개미수열 (Look and Say Sequence)

양의 정수 n(3 < n < 100)이 주어질 때, n번째 항의 가운데 두 자리를 반환합니다.

```
n=5  ->  L5 = 111221      ->  "12"
n=8  ->  L8 = 1113213211  ->  "21"
```

## 실행

```bash
pnpm install
pnpm --filter algorithm test
```

TypeScript로 작성했고 테스트는 Vitest를 사용했습니다. 저장소는 pnpm 워크스페이스로 구성되어 있습니다.

## 풀이

'1'에서부터 n회 반복하여 다음 항을 누적 도출합니다.
이전 항을 읽는 로직은 재사용이 가능하기 때문에, 재귀 함수를 활용하였습니다.

`reduce`로 한 번만 순회하면서 연속 구간을 누적하고, 현재 문자가 다음 문자와 다를 때만 새 묶음을 엽니다.

n이 2 이상일 때 각 항은 (개수)(숫자) 쌍의 나열이라 길이가 항상 짝수입니다.
따라서 가운데 두 자리는 `slice(mid-1, mid+1)`로 바로 얻을 수 있습니다.

## 복잡도

항의 길이는 한 단계마다 약 1.3배씩 늘어납니다.
실제로 측정해보니 1.3036배였고, 알려진 Conway 상수(1.303577)와 거의 일치했습니다.

- 시간: O(1.3^n). 각 단계에서 항 전체를 한 번씩 훑습니다.
- 공간: O(1.3^n). 최종 항 문자열을 그대로 들고 있어야 합니다.
- 재귀 깊이: O(n). n이 100 미만이라 스택 한계와는 무관합니다.

### 실측

| n | 길이 | 시간 |
|---|---|---|
| 40 | 63,138 | 6ms |
| 50 | 894,810 | 103ms |
| 55 | 3,369,156 | 507ms |
| 60 | 12,680,852 | 2,234ms |
| 62 | - | 힙 부족으로 종료 (4GB 기준) |

n=62에서 메모리 한계에 부딪힙니다.
위 증가율로 계산하면 n=99의 항 길이는 약 4천억 자에 달해서, 문자열을 전부 만드는 방식으로는 도달할 수 없습니다.

## 한계와 개선 방향

전체 문자열을 만들지 않고, 길이만 계산해서 가운데가 속한 구간으로 좁혀 들어가는 방식이 필요합니다.

항을 특정 위치에서 자르면 이후 단계에서도 양쪽이 서로 영향을 주지 않는 지점이 있습니다.
이런 지점을 찾을 수 있다면 조각별 길이만 구해서 목표 위치가 속한 조각만 따라가면 됩니다.
같은 조각이 반복해서 나오기 때문에 조각과 남은 단계 수를 키로 길이를 저장해두고 재사용할 수도 있습니다.

다만 어디를 잘라도 되는지 판정하는 게 간단하지 않았습니다.
경계에 놓인 숫자만 비교해서는 부족했고, 직접 실험해보니 경계상으로는 문제가 없어 보이는 지점이 7단계가 지나서야 깨지는 경우도 있었습니다.
몇 단계까지 확인해야 충분한지 근거를 세우지 못해서 이번 제출본에서는 넣지 않았습니다.

## 테스트

문제의 예시 표(n=1~8)를 먼저 테스트로 옮기고 실패를 확인한 뒤 구현하는 순서로 진행했습니다.
예시에 없는 n=50 케이스는 처리 가능한 상한 부근을 확인하기 위해 추가했습니다.

```
Tests  9 passed (9)   297ms
```

## 소감

단순히 생성하는 방식으로는 3 < n < 100 범위의 개미수열을 모두 구하는 것이 어려웠습니다.
수열의 패턴을 먼저 파악해보려 했지만 직관적으로 잡히지 않아서, n이 1인 경우부터 순차적으로 다음 항을 구해나가는 방식으로 접근했습니다.
이전 항에서 다음 항을 만드는 로직은 매 단계 동일하기 때문에, 재귀 함수로 재사용하는 편이 적절하다고 판단했습니다.

구현을 마친 뒤 어느 지점까지 감당할 수 있는지 직접 측정해보면서, 항의 길이가 생각보다 훨씬 빠르게 늘어난다는 것을 체감했습니다.
n=60까지는 2초 남짓이면 끝나는데 두 단계만 더 가도 메모리가 버티지 못했습니다.
동작하는 코드를 만드는 것보다, 그 코드가 어디서 무너지는지 알아내는 과정에서 배운 것이 더 많았습니다.
